<Callout type="info" title="Sample local results">
  The numbers on this page are from a local benchmark run against the
  generated fixture PDFs, on an AMD Ryzen 7 7800X3D (16 threads) running Linux
  x64. Treat them as sample measurements, not universal guarantees.
</Callout>

## What the benchmark compares

The benchmark currently compares three implementations on the same input PDFs
and settings:

- `pdf-raster`
- `pdfjs-dist + @napi-rs/canvas`
- `pdfjs-dist + node-canvas`

## Run it

```bash
bun run benchmark
```

Useful flags:

- `--libs <list>` runs a comma-separated subset of `pdf-raster`,
  `pdfjs-napi` and `pdfjs-node-canvas` (default: all three).
- `--concurrency <n>` starts `n` simultaneous `convert()` calls per measured
  run and reports pages per second. It applies to `pdf-raster` only; the
  pdf.js backends always run at concurrency 1.

```bash
bun run benchmark -- --libs pdf-raster --output jpeg --concurrency 4
```

## Default settings

<Steps>
  <Step>
    Use two deterministic, generated US-letter fixtures written to
    `benchmark/.fixtures/` (git-ignored): `text-20.pdf` (20 text pages) and
    `mixed-10.pdf` (10 pages alternating text and a 1200x900 image). Pass PDF
    paths explicitly to benchmark your own files. `bun run --cwd benchmark
    fixtures` regenerates them.
  </Step>
  <Step>
    Render at `dpi=300` with `output=png`.
  </Step>
  <Step>
    Execute one warmup run, then repeated measured runs for each backend.
  </Step>
</Steps>

<Callout type="warning" title="node-canvas requirement">
  The benchmark workspace includes both `@napi-rs/canvas` and `node-canvas`.
  Depending on your machine, `node-canvas` may require native system
  prerequisites before the benchmark can run successfully.
</Callout>

## Output size

The `Avg bytes` column is the total output per run. pdf-raster's PNG output
favours speed (fast compression), so its files are about 3x larger than the
PNGs `pdfjs-dist` produces (59.7 MB vs 20.8 MB for the 20 `text-20` pages).

Average output size per page for pdf-raster at 300 DPI:

| Format        | text-20 | mixed-10 |
| :------------ | :------ | :------- |
| PNG           | 3055 KB | 5441 KB  |
| WebP (lossless) | 969 KB  | 2348 KB  |
| JPEG (q75)    | 1224 KB | 1121 KB  |

WebP is lossless and smallest on the text PDF; JPEG is lossy and smallest on
the image-heavy PDF.

## Throughput and concurrency

`--concurrency <n>` starts `n` simultaneous `convert()` calls per measured run
(pdf-raster only) and reports pages per second across all of them:

```bash
bun run benchmark -- --libs pdf-raster --output jpeg --concurrency 4
```

pdf-raster throughput on `text-20.pdf` and `mixed-10.pdf` at 300 DPI, in pages
per second (same machine), with 1 and 4 concurrent calls:

| Format | Concurrency | text-20 | mixed-10 |
| :----- | :---------- | :------ | :------- |
| PNG    | 1           | 59.1    | 39.7     |
| PNG    | 4           | 60.8    | 42.0     |
| JPEG   | 1           | 48.4    | 32.5     |
| JPEG   | 4           | 58.7    | 39.5     |
| WebP   | 1           | 53.8    | 36.3     |
| WebP   | 4           | 56.6    | 38.8     |

Compared with 0.1.x on the same machine, JPEG went from 7.0 to 48.4 pages/s and
PNG from 31.7 to 59.1 pages/s on `text-20.pdf` at concurrency 1. See
[Concurrency and memory](/docs/runtime-and-environment#concurrency-and-memory)
for how rendering, encoding and memory behave under load.

## How to read the multipliers

The relative speed line is a multiplier, not a percentage.

- If the benchmark says `13.04x`, it means the comparison backend took `13.04`
  times as long on that metric.
- In other words, `pdf-raster` was `13.04x` faster on that sample.

## What this benchmark is useful for

- compare end-to-end conversion speed on the included fixtures
- spot regressions between local runs
- compare the current PDFium-based package against `pdfjs-dist` canvas
  backends

Use it as a practical engineering comparison tool, not as a universal claim
about every PDF or every deployment environment.
